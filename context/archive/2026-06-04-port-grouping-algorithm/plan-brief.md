# Port Grouping Algorithm — Plan Brief

> Full plan: `context/changes/port-grouping-algorithm/plan.md`
> Research: `context/changes/port-grouping-algorithm/research.md`

## What & Why

Re-implement the legacy Bun/CSV grouping algorithm as a **pure, deterministic, edge-safe** function in `src/lib/grouping/`, fed from Supabase, persisting ranked "compatible course groupings" into the purpose-built `course_groupings` tables. This is the PRD's recommendation rule (FR-013) and roadmap **F-03** — the draggable building blocks every downstream placement slice depends on.

## Starting Point

The schema landed in commit `ee92448` and the destination tables (`course_groupings`, `course_grouping_members`, `course_overlaps`, `course_merges`) are ready and empty. There is **no existing solver** in `src/` — this is additive greenfield logic. The app uses Supabase only for auth today, so this writes the first real data-query pattern. The legacy algorithm lives in `legacy-grouping-algorithm/src/`; the dp2 CSV fixtures and the golden output `data/out/dp2-variants-2.csv` are in the repo.

## Desired End State

A pure `computeGroupings(subjects)` in `src/lib/grouping/`, fed by two adapters (CSV fixtures for parity, Supabase for runtime), with a `POST /api/grouping` endpoint that loads a cohort's catalog, computes groupings in request scope, and persists deduped results (with a `catalog_hash`) into the existing tables. Correctness is proven by a golden-parity script and a dual-adapter cross-check. No authoring UI yet (that's S-06).

## Key Decisions Made

| Decision | Choice | Why | Source |
| --- | --- | --- | --- |
| Scope | Pure function + compute endpoint (not UI) | Delivers a runnable, testable F-03; S-06 UI builds on top | Plan |
| Determinism | Deterministic enumeration of maximal compatible sets | F-03 requires deterministic output; random-greedy is the limit case of full enumeration | Research + Plan |
| Parity definition | Semantic & directional: golden ⊆ deterministic output | Golden was generated by the *unseeded random* algo → byte-parity is impossible | Plan |
| Persistence | Materialized tables + `catalog_hash` column | Schema is purpose-built for this shape; hash drives S-06 out-of-date detection | Research + Plan |
| Partial catalog | Degrade gracefully + per-grouping warnings | Catalog is built incrementally across slices; refusing would block usefulness | Plan |
| Test runner | Add Vitest (project's first); unit tests gate CI | The pure core is the ideal first test target; "no runner yet" is a reason to add one | Plan |
| Test tiers | Unit (CI, pure) + integration (local, needs Supabase) | DB-dependent checks can't run in CI; pure parity/core tests can and should | Plan |

## Scope

**In scope:** Vitest harness + CI wiring (project's first test runner), pure grouping core, deterministic enumeration, verbatim scoring, CSV fixture adapter + golden parity test, Supabase catalog adapter, `catalog_hash` migration, dp2 dev seed, dual-adapter cross-check, dedup→upsert persistence, `POST /api/grouping`, staleness helper.

**Out of scope:** S-06 authoring UI, the ≤200 ms online validator, new collision classes, JSONB/compute-on-read persistence, queued compute, React component / E2E tests + broad test backfill, workerd test pool, keeping the Bun/CSV file layer at runtime.

## Architecture / Approach

**Two adapters, one core.** The pure core takes `Subject[]` → ranked variants and is unit-tested under Vitest (Node env). The CSV fixture adapter mirrors legacy assembly so the golden-parity test feeds the exact golden-producing input. The Supabase adapter produces the same `Subject[]` from live rows. A dev dp2 seed lets the two adapters be cross-checked on identical data — which doubles as the definitive validation of the `course_overlaps` direction. The endpoint composes Supabase adapter + core + persistence in request scope.

## Phases at a Glance

| Phase | What it delivers | Key risk |
| --- | --- | --- |
| 0. Test harness | Vitest + config + CI unit-test step + CLAUDE.md update + smoke test | Vite/alias config; keeping CI fast and DB-free |
| 1. Core + parity gate | Pure deterministic algorithm + unit tests + golden ⊆ output test | Enumeration must reproduce golden semantics; combinatorial blowup |
| 2. Supabase + persistence | catalog_hash migration, runtime loader, dp2 seed, dual-adapter cross-check, dedup upsert | Faithful DB→domain mapping; overlap direction correctness |
| 3. Endpoint + guards | `POST /api/grouping`, staleness helper, warnings, CPU measurement | Workers CPU ceiling at full-cohort scale |

**Prerequisites:** F-02 schema (done, `ee92448`); local Supabase stack for Phases 2–3 integration tests.
**Estimated effort:** ~2–3 sessions across 4 phases (Phase 0 is small).

## Open Risks & Assumptions

- **Workers CPU ceiling**: maximal-independent-set enumeration is worst-case exponential. Mitigated by a fail-loud cap and an early dp2-scale measurement; escape hatch is Postgres/queued compute (out of scope).
- **Overlap direction**: schema says *base receives dependent's students*; assumed to match legacy and confirmed by the Phase 2 cross-check.
- **No catalog data seeded by default**: runtime verification depends on the dp2 dev seed; real author data arrives via S-02/S-03/S-04.

## Success Criteria (Summary)

- `pnpm test` passes (unit + golden parity) — the deterministic port reproduces the golden output's groupings and scores, gated in CI.
- The Supabase adapter produces identical subjects to the fixture adapter on dp2 (zero diffs, `pnpm test:integration`).
- `POST /api/grouping` populates `course_groupings` for a cohort within the Workers CPU budget, with warnings on partial data.
