# Port Grouping Algorithm — Implementation Plan

## Overview

Re-implement the legacy Bun/CSV grouping algorithm (`legacy-grouping-algorithm/src/`) as a **pure, deterministic, edge-runtime-safe** function in `src/lib/grouping/`, fed from Supabase catalog state, and persist its ranked output into the already-built `course_groupings` / `course_grouping_members` tables. This is roadmap **F-03**; it stops short of the S-06 authoring UI but delivers a runnable `POST /api/grouping` compute endpoint that S-06 will sit on top of.

The work is greenfield logic against a purpose-built schema — there is no existing solver to reconcile with. The two real design tensions (randomness→determinism, and CPU cadence) are resolved up front: the search becomes a deterministic enumeration, and compute runs one-shot inside a request handler, off the validator's 200 ms hot path.

## Current State Analysis

- **Legacy algorithm** (`legacy-grouping-algorithm/src/index.ts`): for one hardcoded cohort it assembles `Subject {id, name, course, hours, students[], teacher}`, then builds variants per seed subject:
  - `hasIntersection` (`index.ts:8-14`) — two subjects conflict if same id, **shared teacher**, OR **shared student**.
  - `findOptions`/`allList` (`index.ts:16-34`) — random-greedy maximal-independent-set search, repeated up to `tries = 1000`, deduped by sorted-id key (`isUnique`, `index.ts:36-48`).
  - Scoring (`index.ts:54-74`) — `similar` (hours-similarity), `students` (coverage = **sum of per-subject student counts, not a unique union**), `rank` (Σ hours·students); variants sorted by `similar` desc.
  - Output flattened to CSV via `Bun.write` (`index.ts:82-88`, `utils/saveAsCsv.ts`).
- **Subject assembly** (`repository/subjects.ts`): groups student choices by subject, **unions overlap-partner students into the subject** (`findOverlaps`, `subjects.ts:21-22,37`), and adds **virtual merge-parent subjects** whose students are the union of their children (`subjects.ts:42-45`). Subject identity is a composite name string (`subjectName`, `loaders.ts:50-52`).
- **Live schema** (`supabase/migrations/20260602185012_minimal_domain_schema.sql`): the destination tables exist — `course_groupings(plan_id, cohort_id, coverage_count, score)` (L131) and `course_grouping_members(grouping_id, course_id)` (L142), plus dependency tables `course_overlaps(base_course_id, dependent_course_id)` (L51, comment: *dependent's students also attend base*) and `course_merges(parent_course_id, child_course_id)` (L60). `course_groupings` has **no `catalog_hash` column yet**.
- **Supabase usage**: the app currently uses Supabase **only for auth** — there are **no `.from(<table>)` data queries in `src/`**. This port writes the first real data-query pattern. Client factory: `src/lib/supabase.ts:6` (`createClient(headers, cookies)`, returns `null` if env unset). API-route template: `src/pages/api/auth/signin.ts`. Middleware (`src/middleware.ts`) is deny-by-default, so `/api/grouping` is auto-protected.
- **Edge runtime**: Cloudflare workerd, `nodejs_compat`. Bun/`fs` are unavailable; the CSV file layer is **rewritten, not ported**. Pure logic + `utils/array.ts` lift-and-shift. `Math.random` in module scope can be deterministic on workerd → another reason to run compute in request scope.
- **Tooling**: **no test runner exists yet** — this change adds the project's first (**Vitest**, the Vite-native runner; Astro already runs on Vite). The pure grouping core is the ideal first thing to test, so the golden-parity check becomes a real test, not an ad-hoc script. Reference fixtures present: `data/dp2/{students_subjects,teachers_subjects,subjects_overlap,merge_subjects}.csv`; golden output `data/out/dp2-variants-2.csv` (129 KB). The test env runs in Node, so reading these fixtures via `node:fs` in tests is fine (they are never read at runtime).
- **CI** (`.github/workflows/ci.yml`): the `ci` job runs install → `astro sync` → `lint` → `build`. A `test` step (unit only) is added before `build`. The `deploy` job is unchanged.
- **Config**: `tsconfig.json` defines the `@/*` → `./src/*` path alias; the Vitest config must resolve it. No workerd APIs are used by the core, so tests run in the plain Node environment (not the workers pool).

### Key Discoveries

- **The golden file was generated by the *unseeded random* algorithm** — so byte-for-byte parity is impossible once the port is deterministic. Parity is therefore **semantic and directional**: every record in `dp2-variants-2.csv` must appear in the deterministic output with matching coverage + score (golden ⊆ output). Deterministic full enumeration is the limit of the random process (any maximal independent set is greedy-reachable), so this subset relation is the correct, achievable assertion.
- **`coverage_count` = Σ per-course student counts (with cross-course duplicates), NOT a unique union** (`index.ts:62`). Preserve verbatim.
- **Empty-teacher collision bug → handled by the type, not a special case**: legacy sets `teacher = meta?.teacher ?? ""` (`subjects.ts:31`); `hasIntersection` then treats `"" === ""` as a shared teacher. In the legacy data every course had a teacher so this never fired, but the "degrade gracefully" requirement means teacherless courses will exist. Because the core's `teacherKey` is `string \| null` (mirroring nullable `courses.teacher_id`) and the collision predicate only matches **non-null equal** keys, teacherless courses cannot false-collide. A warning is still emitted per teacherless course.
- **Core domain = a projection of the app's `Database` types, not a port of the legacy `Subject`.** The core operates on `GroupingCourse { id; teacherKey; studentKeys; hours }` with **opaque identity tokens** — `course.id`/`student.id` at runtime, the composite name string in fixtures — and carries **no display name**. Names are reconstructed only at the edges that already hold the catalog (parity test, endpoint response). The legacy algorithm's *mechanism* is ported; its *type shape* is not.
- **`course_groupings` is a set of members**, with no seed column — so persistence **dedups variants by member-set** (the same maximal set produced under different seeds collapses to one row, keyed by sorted `memberIds`). Parity is asserted on the *pure core output*, before this dedup.

## Desired End State

`src/lib/grouping/` contains a pure `computeGroupings(courses)` function that, given a catalog snapshot as a `GroupingCourse[]` projection, returns a deterministic ranked list of compatible groupings (keyed by member ids) reproducing the legacy output's groupings and scores. Two adapters feed it: a CSV fixture adapter (for the parity gate) and a Supabase adapter (for runtime). `POST /api/grouping` loads a cohort's catalog from Supabase, computes groupings in request scope, persists deduped results (with a `catalog_hash`) into `course_groupings`/`course_grouping_members`, and returns the ranked list plus any partial-data warnings. Correctness is proven two ways: the Vitest golden-parity test passes under `pnpm test` (golden ⊆ output), and the CSV adapter and Supabase adapter produce the same `GroupingCourse[]` projection (aligned on the composite-name natural key) for the seeded dp2 catalog.

Verification: `pnpm build` (CI gate) passes; `pnpm lint` passes; `pnpm test` is green (incl. the golden-parity test); the dual-adapter cross-check reports zero diffs (`pnpm test:integration`); a `POST /api/grouping` against the seeded dp2 catalog populates `course_groupings` with sane row counts and completes within the Workers CPU budget.

## What We're NOT Doing

- **No S-06 authoring UI** — no "Compute groupings" button, no ranked-list rendering, no visual "out of date" badge. The plan provides the endpoint and a staleness *helper* the UI will later call.
- **No validator / online per-drop logic** — the ≤200 ms collision validator is a separate component built in the placement slices. The combinatorial generator must never be embedded in it.
- **No new collision classes** beyond legacy (shared teacher / shared student within one cohort). Teacher-availability and cross-cohort fixed-teacher classes belong to the validator.
- **No JSONB persistence, no compute-on-read, no queue/Durable Object** — output is materialized into the existing tables (the chosen path). Async/queued compute is a documented scale escape hatch only.
- **No React component / E2E tests, no broad test backfill** — the Vitest harness is introduced, but this change only tests the grouping core (unit) and the adapter/endpoint paths (integration, local). Component and end-to-end testing remain for Module 3.
- **No workerd test pool** — the core is plain TS with no workers APIs, so tests run in Node; `@cloudflare/vitest-pool-workers` is not adopted here.
- **No keeping the Bun/CSV file layer at runtime** — `data/dp2/*.csv` remain only as reference fixtures for the parity test and dev seed.

## Implementation Approach

Two adapters, one core. The **pure core** (`src/lib/grouping/`) knows nothing about Supabase, Astro, or CSVs — it takes `GroupingCourse[]` (a projection of the app's `Database` types, identity as opaque tokens) and returns ranked variants keyed by member ids, runnable under plain Node for the parity gate. The **CSV fixture adapter** mirrors the legacy `loaders.ts` + `subjects.ts` assembly (using the composite name as the opaque id) so the parity test feeds the core the exact input that produced the golden. The **Supabase adapter** produces the same `GroupingCourse[]` projection from live catalog rows (ids = `course.id`), plus an id→name map for display. A dev seed loads the dp2 fixtures into local Supabase so the two adapters can be cross-checked on identical data (aligned on the composite-name natural key) — which simultaneously resolves the `course_overlaps` direction question and validates the entire DB→domain mapping. The compute endpoint composes the Supabase adapter + core + persistence.

Phases are ordered by risk, behind a one-time harness setup: **Phase 0** stands up Vitest + CI wiring so correctness can be *tested*, not just scripted; then correctness first (Phase 1, validated against the golden with zero I/O), then the data layer (Phase 2), then the request surface (Phase 3). Unit tests (pure core + golden parity) are fast, deterministic, and gate every PR via CI. Integration tests (dual-adapter cross-check, endpoint) require the local Supabase stack and run locally / opt-in, kept out of CI.

## Critical Implementation Details

- **Determinism replaces randomness.** Drop `randomElement` and the 1000-retry loop. Enumerate **all maximal independent sets containing each seed subject**, iterating candidates in a stable id-sorted order, deduped by sorted-id key. (Complement-graph maximal-clique enumeration à la Bron–Kerbosch with a deterministic pivot is the textbook form; the implementer picks the concrete shape.) Final variant ordering: `similar` desc, then a deterministic tie-break (`coverage_count` desc, then the sorted member-`id` list) so output is fully reproducible.
- **Enumeration guard (fail loud, no silent cap).** Maximal-independent-set enumeration is worst-case exponential. Include an explicit ceiling on enumerated sets per seed; if exceeded, **throw / log which seed and how many** rather than silently truncating. Measure against the real dp2 catalog in Phase 3 before trusting it at full-cohort scale; if it blows up, the documented escape hatch is Postgres-side compute or queued compute (out of scope here).
- **Null teacher ≠ shared teacher.** In the collision predicate, two courses share a teacher only when both `teacherKey`s are **non-null and equal**. Modeling `teacherKey` as `string \| null` (not a `''` sentinel) is what enforces this — it deviates from the literal legacy `===` to support the degrade-gracefully decision; emit a warning for any teacherless course rather than letting it collide with every other teacherless course.
- **`coverage_count` is a sum, not a union** — preserve `Σ course.studentKeys.length` verbatim, including students counted once per course they appear in.
- **Compute runs in request scope**, never at module load (workerd may freeze `Math.random` globally, and there is no request context at init). No top-level `await`.
- **`catalog_hash`** is a stable SHA-256 (via Web Crypto `crypto.subtle.digest`, edge-safe) over a canonical, sorted serialization of the catalog snapshot (course ids + hours + teacher, sorted student-choice pairs, overlaps, merges). It drives S-06's out-of-date detection.

## Phase 1: Pure deterministic grouping core + golden parity gate

### Overview

Lift the algorithm into `src/lib/grouping/` with collision rules and scoring preserved verbatim, the random search replaced by deterministic enumeration, and prove correctness against the golden file via Vitest unit tests — all with zero runtime I/O (tests read fixtures from disk in Node).

### Changes Required

#### 1. Domain types

**File**: `src/lib/grouping/types.ts`

**Intent**: Define the core's domain contract as a **projection of the app's generated `Database` types** (not a port of the legacy `Subject` shape). Identity is an opaque token — `course.id` at runtime, the `(name, level, group)` composite string in fixtures — and the core never carries a display name. Display names are joined at the edges (parity test, endpoint response) that already hold the catalog.

**Contract**: `GroupingCourse { id: string; teacherKey: string \| null; studentKeys: string[]; hours: number }` — a view over `courses` (`id`, `teacher_id`, `hours_per_week`) + `student_choices` (`student_id`); tokens are opaque, the core never parses them. `teacherKey` is `string \| null` (mirrors `courses.teacher_id`, which is nullable in `database.types.ts`). `GroupingVariant { size: number; coverageCount: number; rank: number; score: number; memberIds: string[] /* member ids, seed first */ }` — **ids are the spine**; no display names. `GroupingResult { seedId: string; variants: GroupingVariant[] }`. `ComputeWarning { courseId: string; kind: 'no-teacher' | 'no-students' | 'zero-hours'; message: string }`. The legacy `Subject` type is **not** ported; this projection replaces it.

#### 2. Collision predicate

**File**: `src/lib/grouping/collision.ts`

**Intent**: Port `hasIntersection`'s logic; the empty-teacher fix becomes type-level, not a special case.

**Contract**: `hasIntersection(course: GroupingCourse, list: GroupingCourse[]): boolean` — true if same `id`, OR a teacher shared with any list member where **both `teacherKey`s are non-null and equal**, OR any shared `studentKey`. (Legacy `index.ts:8-14`.) Because `teacherKey` is `string \| null`, the legacy `"" === ""` empty-teacher collision simply cannot occur — `null` never equals `null` under the non-null guard — so the deviation is expressed by the type rather than documented as an exception.

#### 3. Deterministic enumeration

**File**: `src/lib/grouping/enumerate.ts`

**Intent**: Replace `findOptions`/`allList`/`randomElement` with deterministic enumeration of all maximal compatible sets containing a seed.

**Contract**: `enumerateVariants(seed: GroupingCourse, all: GroupingCourse[], cap: number): GroupingCourse[][]` — returns every maximal independent set (in the conflict graph) that contains `seed`, candidates visited in id-sorted order, deduped by sorted-id key. Throws a descriptive error if the count would exceed `cap`. No `Math.random`.

#### 4. Scoring

**File**: `src/lib/grouping/score.ts`

**Intent**: Port the variant scoring verbatim.

**Contract**: Given a `GroupingCourse[]` set and its seed, produce `GroupingVariant` with `score` = `similar` (`Math.round(avg(round(hours/maxHours*100)))/100`, `index.ts:54-58`), `coverageCount` = `Σ studentKeys.length` (`index.ts:62`), `rank` = `Σ hours·studentKeys.length` (`index.ts:63`), `memberIds` = seed `id` first then the other members' `id`s in a deterministic order (sorted by `id` via `localeCompare`; legacy sorted by name at `index.ts:65-71`, but the core no longer holds names — name-based display ordering is reapplied at the edges that join names).

#### 5. Core entry + utils

**File**: `src/lib/grouping/index.ts`, `src/lib/grouping/utils.ts`

**Intent**: Compose the pieces into the pure public entry; lift `groupBy`/`unique` from legacy `utils/array.ts` (drop `randomElement`).

**Contract**: `computeGroupings(courses: GroupingCourse[], opts?: { cap?: number }): GroupingResult[]` — per seed, enumerate → score → sort by `score` desc then deterministic tie-break (`coverageCount` desc, then the sorted member-`id` list); mirrors legacy `results` shape (`index.ts:50-80`) but keyed by `seedId`/`memberIds`. Pure, no imports of `astro:*`/Supabase, uses only relative imports so it runs under Node type-stripping.

#### 6. CSV fixture adapter

**File**: `src/lib/grouping/adapters/fixture.ts`

**Intent**: Reproduce legacy `loaders.ts` + `subjects.ts` assembly (composite `subjectName`, overlap-student union, virtual merge subjects) reading `data/dp2/*.csv`, so the parity test feeds the core the exact golden-producing input — emitted as `GroupingCourse[]`.

**Contract**: `loadFixtureCourses(dir: string): GroupingCourse[]` — parses the four CSVs (a tiny inline CSV split is enough; `csv-simple-parser` is not a dependency), applies `subjectName` (`loaders.ts:50-52`), overlap expansion (`subjects.ts:37`), and virtual merge subjects (`subjects.ts:42-45`). The composite `subjectName` string is used as the opaque `id` (so the core's `memberIds` are exactly the tokens the golden file lists — no separate id→name map needed on the fixture path); `teacherKey` = teacher token or `null` (empty teacher → `null`); `studentKeys` = student tokens. **Test/dev-only and Node-only (`node:fs`): the pure core and the endpoint must never import it**, or `node:fs` would be dragged into the workerd bundle. Make the boundary obvious — keep it out of the core's import graph (e.g. name it `fixture.node.ts` or co-locate under a `__fixtures__/`-style path); only tests and dev scripts import it.

#### 7. Golden parity test

**File**: `src/lib/grouping/__tests__/parity.test.ts`

**Intent**: Assert the deterministic core reproduces the golden semantically (golden ⊆ output).

**Contract**: Vitest test. Loads fixture courses (`loadFixtureCourses('data/dp2')`), runs `computeGroupings`, flattens to legacy records `[coverageCount, score, ...memberIds]` (`index.ts:82-86`; on the fixture path `memberIds` **are** the composite name tokens the golden lists), normalizes each to an order-insensitive member-set key + score, and asserts **every** row of `data/out/dp2-variants-2.csv` is present with matching `coverage_count` and `score`. On failure, the assertion message lists missing/mismatched rows. Pure + fs-only → runs in CI.

#### 8. Core unit tests

**File**: `src/lib/grouping/__tests__/{collision,enumerate,score}.test.ts`

**Intent**: Lock the collision rules, deterministic enumeration, and scoring formulas independently of the golden file.

**Contract**: Targeted Vitest cases on small hand-built `GroupingCourse[]` fixtures — `hasIntersection` covers same-id / shared-teacher / shared-student / **null-teacherKey-does-not-collide** (two courses with `teacherKey: null` are not in conflict); `enumerateVariants` covers a known small graph (exact set of maximal compatible sets, determinism across runs, cap-exceeded throws); `score` covers `similar`/`coverageCount` (sum, not union)/`rank`/member-id ordering against worked examples.

### Success Criteria

#### Automated Verification

- Linting passes: `pnpm lint`
- Type/build check passes: `pnpm build`
- Unit + parity tests pass: `pnpm test` (collision/enumerate/score + golden ⊆ output with matching scores)
- Enumeration test asserts determinism (stable output across runs) and cap-exceeded throws

#### Manual Verification

- Spot-check a few high-coverage groupings in the output against `data/out/dp2-variants-2.csv` for plausibility
- Confirm the enumeration completes on dp2 without hitting the cap, and note the largest per-seed variant count

## Phase 2: Supabase integration & persistence

### Overview

Add the `catalog_hash` column, build the runtime catalog loader that produces the same `GroupingCourse[]` projection as the fixture adapter, seed the dp2 fixtures into local Supabase to cross-check the two adapters (resolving the overlap-direction question), and write the dedup→upsert persistence layer.

### Changes Required

#### 1. `catalog_hash` migration

**File**: `supabase/migrations/<timestamp>_course_groupings_catalog_hash.sql`

**Intent**: Give `course_groupings` a hash column for out-of-date detection (the chosen materialized + catalog_hash path; F-02 open question resolved).

**Contract**: `alter table course_groupings add column catalog_hash text;` (nullable — pre-existing rows, if any, have none). Optionally index `(plan_id, cohort_id, catalog_hash)`. Regenerate `src/lib/database.types.ts` afterward (`pnpm exec supabase gen types typescript --local`).

#### 2. Supabase catalog adapter

**File**: `src/lib/grouping/adapters/supabase.ts`

**Intent**: Load a cohort's catalog from Supabase and assemble `GroupingCourse[]` (the same projection the fixture adapter emits), keyed by `course.id`/`student.id`, plus the id→name map the endpoint and cross-check need.

**Contract**: `loadCohortCourses(supabase, cohortId: string): Promise<{ courses: GroupingCourse[]; names: Map<string, string>; warnings: ComputeWarning[] }>`. Queries mirror `supabase/snippets/students_subjects.csv.sql` and `teachers_subjects.csv.sql` (joins for choices + course meta), plus `course_overlaps` and `course_merges` for the cohort's courses, typed against the generated `Database` types. Builds `GroupingCourse` per course: `id` = `course.id`, `studentKeys` = student_ids from `student_choices` **unioned with overlap-partner students** (direction per the schema comment: *base receives dependent's students*), `teacherKey` = `teacher_id` (kept as `null` when absent — **no `''` sentinel**), `hours` = `hours_per_week`. Adds virtual merge-parent courses (`studentKeys` = union of children). `names` maps each `course.id` → reconstructed composite (`name` + `level` sentinel `'none'` + `group_index` sentinel `0`) for display/response and cross-check alignment. Emits `warnings` for teacherless / studentless / zero-hour-non-merge courses.

#### 3. Dev seed for dp2

**File**: `supabase/seed-dp2.sql` (or `scripts/seed-dp2.ts`) — dev-only, not part of the default `seed.sql`

**Intent**: Insert the dp2 catalog (Year 2 cohort, teachers, courses, students, choices, overlaps, merges) derived from `data/dp2/*.csv` so the runtime path is exercisable and the adapters can be cross-checked on identical data.

**Contract**: Idempotent inserts mapping each CSV to its tables (the inverse of the `snippets/*.sql` projections). Loadable against the local stack (`supabase db reset` + apply, or `psql`). Documented as dev-only in the file header.

#### 4. Dual-adapter cross-check (integration test)

**File**: `src/lib/grouping/__tests__/adapter-parity.integration.test.ts`

**Intent**: Prove the Supabase mapping is faithful by asserting `loadCohortCourses` (dp2 cohort) and `loadFixtureCourses` (`data/dp2`) produce the same domain projection. The two adapters use different identity tokens (UUIDs vs name strings), so the comparison aligns them on the **natural key** — the composite name (the fixture's `id`, and the Supabase adapter's `names` value) — then compares the real domain fields.

**Contract**: Vitest **integration** test (`*.integration.test.ts`, excluded from CI / `pnpm test`, run via `pnpm test:integration`). Connects to the local Supabase stack via a **test-only client built with the `service_role` key** (read from a local-only test env var, e.g. `SUPABASE_SERVICE_ROLE_KEY` in `.envs/` / `.env.test.local`) — service_role bypasses RLS, so the `authenticated`-only policies don't block the test's direct reads. The key is local/secret: never committed, never in the client bundle, never in CI. Loads both adapters, joins courses by composite name, and asserts zero diffs across `studentKeys` membership (mapped student tokens), `teacherKey` presence/identity, and `hours`. Skips with a clear message if the local stack/env is unavailable. **This is the definitive check of the `course_overlaps` base/dependent direction** (research Open Q3).

#### 5. Persistence layer

**File**: `src/lib/grouping/persist.ts`

**Intent**: Dedup variants by member-set and upsert into the existing tables with a catalog hash.

**Contract**: `computeCatalogHash(snapshot): Promise<string>` (SHA-256 via Web Crypto over canonical sorted serialization). `persistGroupings(supabase, { planId, cohortId, catalogHash, results }): Promise<void>` — flatten `results` to **distinct member-sets** (collapse same set across seeds, keyed by the sorted `memberIds`), then **delegate the write to a single atomic RPC** (`supabase.rpc('replace_cohort_groupings', { p_plan_id, p_cohort_id, p_catalog_hash, p_groupings })`) rather than issuing separate `.from().delete()`/`.from().insert()` calls — PostgREST has no client-side transaction, so a delete followed by a failed insert would wipe the cohort's groupings. Because the core's `memberIds` **are** `course.id`s at runtime, the payload carries `course.id`s directly — no name→id reverse lookup. The RPC (see migration below) deletes prior `(plan_id, cohort_id)` rows and inserts the new groupings + members in one transaction.

#### 6. Atomic-replace RPC

**File**: `supabase/migrations/<timestamp>_replace_cohort_groupings_fn.sql`

**Intent**: Make the persistence replace atomic, which supabase-js/PostgREST cannot do across calls.

**Contract**: `create function replace_cohort_groupings(p_plan_id uuid, p_cohort_id uuid, p_catalog_hash text, p_groupings jsonb) returns void language plpgsql` — in one transaction, deletes existing `course_groupings` for `(p_plan_id, p_cohort_id)` (members cascade via FK) and inserts one row per grouping (`coverage_count`, `score`, `catalog_hash`) plus its `course_grouping_members`. **`SECURITY INVOKER`** (the default — do **not** use `SECURITY DEFINER`) so the existing `authenticated` RLS policies still gate the write. Regenerate `database.types.ts` so the `.rpc()` call is typed.

## Phase 3: Compute endpoint & guards

### Overview

Expose `POST /api/grouping`, composing the Supabase adapter + core + persistence, with partial-data warnings, a staleness helper, error handling, and a CPU measurement against dp2-scale data.

### Changes Required

#### 1. Compute endpoint

**File**: `src/pages/api/grouping.ts`

**Intent**: One-shot, request-scoped compute that loads → computes → persists → returns the ranked list.

**Contract**: `POST` (`APIRoute`, pattern from `src/pages/api/auth/signin.ts`) accepting JSON `{ planId: string; cohortId: string }`. Creates the Supabase client (`createClient`, null-guard → 503/JSON error), validates plan + cohort exist, calls `loadCohortCourses` → `computeGroupings` (in handler scope) → `computeCatalogHash` → `persistGroupings`, and returns JSON `{ groupings: GroupingResult[], names: Record<string, string>, catalogHash, warnings }` — `groupings` are id-keyed (`seedId`/`memberIds`); the `names` map (from `loadCohortCourses`) lets S-06 render labels without re-querying. Auto-protected by deny-by-default middleware (no allowlist change). Returns structured errors (400 bad input, 404 missing plan/cohort, 422 if the enumeration cap is hit, 503 if Supabase unconfigured).

#### 2. Staleness helper

**File**: `src/lib/grouping/staleness.ts`

**Intent**: Provide the out-of-date primitive S-06 will surface in the UI (no UI here).

**Contract**: `isGroupingStale(supabase, { planId, cohortId }): Promise<boolean>` — computes the current catalog hash and compares it to the stored `catalog_hash` on the latest `course_groupings` rows for `(plan_id, cohort_id)`; true if absent or mismatched.

#### 3. Partial-data degrade behavior

**File**: `src/lib/grouping/adapters/supabase.ts` (warnings already emitted), endpoint passthrough

**Intent**: Compute with whatever catalog exists and report gaps rather than refusing.

**Contract**: Endpoint includes `warnings` in the response; teacherless courses don't false-collide (collision fix from Phase 1); missing hours default to 0 (legacy `?? 0`). No blocking on partial catalogs.

#### 4. Endpoint integration test

**File**: `src/lib/grouping/__tests__/endpoint.integration.test.ts`

**Intent**: Exercise the full request path against the seeded dp2 catalog (local only).

**Contract**: Vitest integration test (excluded from CI). Uses the same `service_role` test client as the adapter-parity test (bypasses RLS for setup/assertions). Invokes the compute path for the dp2 cohort, asserts `course_groupings`/`course_grouping_members` are populated with the deduped sets and that the response carries the ranked list + `catalogHash`. Skips if the local stack is unavailable. (Faithful end-to-end RLS coverage — a seeded authenticated session through the real middleware — is deferred to the Module 3 testing work, per scope.)

## Testing Strategy

This change introduces **Vitest** as the project's first test runner (Phase 0). Two tiers:

### Unit tests (CI gate — `pnpm test`, pure, no DB)

- `__tests__/{collision,enumerate,score}.test.ts` — collision rules (incl. empty-teacher fix), deterministic enumeration (exact sets, determinism, cap-throws), and scoring formulas on small hand-built fixtures.
- `__tests__/parity.test.ts` — golden ⊆ deterministic output on the dp2 fixtures, with matching coverage/score (the F-03 correctness gate). Reads `data/dp2/*` + `data/out/dp2-variants-2.csv` via `node:fs`.

### Integration tests (local / opt-in — `pnpm test:integration`, requires local Supabase)

These connect with a **`service_role` client** (local-only `SUPABASE_SERVICE_ROLE_KEY`), which bypasses the `authenticated`-only RLS policies so direct reads/writes work without a session. The key is never committed or used in CI; tests skip cleanly when it (or the stack) is absent.

- `__tests__/adapter-parity.integration.test.ts` — Supabase adapter output ≡ fixture adapter output on the seeded dp2 catalog (validates the DB→domain mapping, incl. overlap direction). Skips cleanly if the stack is down.
- `__tests__/endpoint.integration.test.ts` — `POST /api/grouping` against the seeded dp2 catalog populates `course_groupings` and returns the ranked list + warnings.

### Manual testing steps

1. `pnpm test` — confirm unit + parity suite is green.
2. Seed dp2 into local Supabase; `pnpm test:integration` — confirm adapter cross-check zero diffs and endpoint test passes.
3. `pnpm dev`, authenticate, `POST /api/grouping` with the dp2 cohort; inspect the JSON and the `course_groupings` rows.
4. Time the request; verify it is comfortably under the Workers CPU budget.
5. Drop a teacher from one course; re-run; confirm a `no-teacher` warning and that groupings still compute.
6. Mutate a course; check `isGroupingStale` returns `true`; re-run compute; check it returns `false`.

## Performance Considerations

Grouping is a deliberate one-shot, cached, off-hot-path computation (roadmap `roadmap.md:22,224`) — the ≤200 ms budget is the validator's, not this generator's. The real risk is the **Workers CPU ceiling** for maximal-independent-set enumeration on large catalogs. Mitigations: the fail-loud enumeration cap, an early CPU measurement on the real dp2 catalog (Phase 3), and the documented escape hatch (Postgres-side or queued compute) if the single-request budget is exceeded at full-cohort scale.

## Migration Notes

Two additive migrations: (1) `course_groupings.catalog_hash` (nullable `text`); (2) the `replace_cohort_groupings` `SECURITY INVOKER` function for atomic persistence. No data backfill needed (the table is unpopulated). Regenerate `src/lib/database.types.ts` after applying (picks up both the column and the RPC signature).
